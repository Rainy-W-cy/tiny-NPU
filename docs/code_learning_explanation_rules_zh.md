# tiny-NPU 代码学习讲解规范

## 1. 适用范围

当用户要求逐步学习、解释、复盘或整理 tiny-NPU 仓库中的脚本、C++ Host、微码、RTL、数据布局和推理流程时，必须遵循本规范。

本规范的目标是让每轮讲解都满足：代码依据明确、章节边界准确、细节深度稳定、示例足够具体、学习状态与 Notion 文档一致。

### 既有内容兼容原则

已经由用户确认、写入 Notion 或形成稳定章节的内容，是后续讲解的风格与层级基线。本规范用于减少遗漏和边界错误，不用于机械重写既有文档。

1. 优先延续既有页面的标题层级、编号方式、讲解节奏和术语。
2. 新章节只补充当前需要学习的内容，不因检查清单存在就重复已经确认的解释。
3. 规范与用户当前明确要求不一致时，以用户当前要求为准，并在必要时更新规范。
4. 规范与代码事实不一致时，以当前仓库代码为准，并修正规范或文档。

## 2. 每轮开始前的检查

每轮讲解开始前必须先完成以下检查，并用一句简短说明告诉用户结果：

1. 确认本轮要讲的文件、函数、代码范围和调用位置。
2. 只读取本轮直接相关的代码，不扩展到无关 RTL 或仿真文件。
3. 检查当前内容是否已经形成完整章节，判断为“暂不适合写文档”或“适合写文档”。
4. 未经用户确认，不因为内容看起来完整就自动写入 Notion；用户明确要求写入时可以直接执行。
5. 若上一轮存在边界错误或遗漏，先修正，再继续新内容。

推荐开场格式：

```text
文档检查：当前内容尚未形成完整章节，本轮先完成 XXX，结束后再次判断是否适合写入。
```

或：

```text
文档检查：当前内容已经形成完整章节，适合写入；本轮先按代码核对最终版本。
```

## 3. 章节信息清单与推荐顺序

下面是章节应覆盖的信息和推荐顺序，不要求每轮输出机械地创建 11 个标题。应根据本轮范围自然组织；没有对应内容、前文已经确认或计划在后续专题学习时可以省略，但不能打乱代码执行顺序。

1. **章节定位**：文件、函数、代码行和本节边界。
2. **本节目标**：说明这一段代码解决什么问题。
3. **输入与前置状态**：进入本节前已有的数据、对象或硬件状态。
4. **调用位置**：明确函数在何处被调用，不能只展示函数定义。
5. **函数实现**：按实际代码顺序解释关键语句、循环和分支。
6. **数据与存储**：说明 shape、展平方式、类型、字节数、offset、地址和所有者。
7. **具体示例**：使用小尺寸数据走一遍索引、地址或控制流程。
8. **输出与结束状态**：说明本节结束后产生了什么。
9. **边界声明**：明确本节尚未执行什么，避免把后续操作提前归入本节。
10. **Review 检查点**：列出用户应当能够回答的关键问题。
11. **下一步**：只给出紧邻的下一段代码，不提前跳到远处模块。

## 4. 函数讲解最低要求

当某个函数是本轮的主要学习对象，或不理解其内部行为就无法理解当前步骤时，不能只写函数名和一句用途。至少需要说明：

1. 函数定义位置。
2. 函数调用位置。
3. 输入参数及其来源。
4. 返回值或输出数据。
5. 内部关键步骤及执行顺序。
6. 失败、为空、越界或超时等处理。
7. 执行结束后改变了哪些状态。

如果函数只作为后续步骤、外部依赖或章节边界被提到，本轮只需说明它的职责、是否已经调用以及后续学习位置，不应提前展开内部实现。

必须明确区分：

```text
函数定义：代码具备这个能力，但此处尚未执行。
函数调用：程序运行到这里时，函数才真正执行。
```

## 5. 数据、指针和 shape 讲解规则

当数组、vector、二进制文件、指针、矩阵或 SRAM 数据是本轮理解重点时，应覆盖下列相关问题。第一次引入或用户对该数据存在疑问时完整解释；后续重复出现时可引用前文，只补充本轮新增的 shape、地址或访问行为。

1. 数据真正存在哪里，谁拥有这块内存。
2. 当前变量保存的是数据、首地址、offset，还是逻辑视图。
3. 逻辑 shape 是什么。
4. 物理上如何展平成一维。
5. 元素类型和单元素字节数是什么。
6. 总元素数和总字节数是多少。
7. 起始 offset 或 SRAM 地址是什么。
8. 实际读取大小由谁决定。
9. 二维或多维索引如何转换成一维索引。
10. 是否存在越界、指针失效或布局不一致风险。

例如解释原始指针时，必须明确：

```text
pointer 只保存首地址；
offset 只决定从哪里开始；
shape 和 size 由常量、循环或微码参数约定；
底层容器才真正拥有数据。
```

## 6. 示例要求

以下内容第一次引入、用户表示不清楚，或仅看代码难以建立直观认识时，应给出一个小型示例：

- 多维数组展平。
- token ID 与文本或字节映射。
- 字典、key/value 和查表。
- 文件 offset 与权重地址。
- 指针加法与数组索引。
- GEMM/GEMV 的 shape 和切分。
- GQA 中 Q head 与 KV group 的对应关系。
- SRAM 地址布局和数据搬运。
- prefill、decode 与 full-recompute 的行为差异。

示例优先使用 2 到 4 个元素的小尺寸数据，并完整展示输入、索引计算和输出。示例必须与真实代码公式一致，不能为了简单而改变语义。已经被用户确认理解的同类示例不必每轮重复。

## 7. 软件与硬件边界

讲解 C++ Host、微码和 RTL 时必须明确动作发生在哪一层：

```text
Python：生成权重、token 和 golden 工件。
C++ Host：解析参数、组织数据、生成微码、驱动 DUT。
微码：描述硬件算子的执行顺序和地址参数。
RTL：接收信号和微码，执行实际硬件状态机与计算。
```

不能把 C++ 布尔变量描述成 RTL 端口，也不能把 host 侧 memcpy、查表或参考计算描述成硬件操作。

涉及控制开关时必须追踪完整链路：

```text
Shell 参数 -> C++ 变量 -> C++ 分支 -> 微码/地址选择 -> RTL 操作
```

## 8. 多模式流程讲解

当本轮目标是学习完整推理模式时，full-recompute、prefill 和 decode 必须分别讲解，不能合并成模糊的“推理流程”。每种模式至少说明：

1. 输入序列范围。
2. Embedding 查询范围。
3. 每层处理的 shape。
4. K/V 的计算、写入和读取方式。
5. 使用的微码生成函数。
6. SRAM 中的主要数据区域。
7. 输出 hidden state 的范围。
8. 下一 token 如何回灌。

讲完后再给出对比表，不能先用对比表代替单独流程。

如果本轮只学习参数解析、文件加载、DUT 初始化或某个公共 helper，只讲与当前范围直接相关的模式差异，并把完整模式流程留到对应章节。

## 9. 准确性与章节边界

所有结论必须以当前仓库代码为依据，并遵循以下要求：

1. 不根据常见 Transformer 实现推断当前代码必然如此。
2. 没有查看调用点时，不宣称函数已经在某阶段执行。
3. 没有独立运行记录时，不宣称某条模式“已验证”。
4. 发现前一版错误时明确修正，不用新说法掩盖旧边界。
5. 当前未讲到的内容统一放入“尚未执行”或“待学习”，不提前展开。
6. 代码注释与代码行为冲突时，以实际行为为准，并指出差异。

## 10. 学习与验证状态

统一使用以下状态：

| 状态 | 含义 |
|---|---|
| 未学习 | 尚未开始代码讲解 |
| 学习中 | 已开始，但当前主题尚未完整闭环 |
| 已学习 | 已按代码完成讲解并经过用户理解确认 |
| 待确认 | 用户曾反馈结果，但缺少可对应的记录 |
| 已验证 | 已记录命令、参数、关键输出和结论 |

用户明确表示“理解了”“这一层清楚了”“继续下一步”或确认写入文档，可以视为当前讲解内容已获得理解确认；但这不等同于运行验证。

“已验证”至少需要记录：

1. 执行命令。
2. 关键参数。
3. 对应模式。
4. 关键输出。
5. PASS/FAIL 或一致性结论。

不同模式必须分别留档，不能用一次模糊的“都通过了”同时标记多个模式已验证。

## 11. Notion 文档维护

用户要求写入 Notion 时，必须同步检查：

1. 学习进度总表中的阶段状态和当前学习位置。
2. 阶段主页面的目录、进度、结论和下一步。
3. 专题子页面的目录、Review 检查点、状态和上下级导航。
4. 已学习、学习中、待确认和已验证之间是否冲突。
5. 中文、代码块、公式和链接是否正常。

写入前先读取现有页面，优先局部替换；写入后重新读取并验证。不能只更新子页面而遗漏主页面，也不能为了同步而虚增学习进度。

更新既有页面时必须延续原有章节结构和编号。除非用户要求重组，不能仅为了满足本规范的推荐结构而重写已经确认的内容。

## 12. 输出风格

1. 使用中文讲解，保留代码标识符的原始英文名称。
2. 标题层级稳定，同一章节不要反复改变编号体系。
3. 先讲执行顺序，再讲总结，不用总结代替过程。
4. 代码片段只保留当前解释所需部分。
5. 每个结论紧邻对应代码或示例。
6. 不一次跨越多个阶段，用户确认后再继续。
7. 用户指出某处不清楚时，先重讲该处，不继续追加新内容。
8. 不把“函数存在”“数据已加载”和“硬件已执行”混为一谈。
9. 以用户已经认可的 0.1 至 0.4 学习页面为当前讲解风格基线，保持自然叙述，不输出机械检查表。
10. 检查清单用于输出前自检，不要求逐项显示给用户。

## 13. 每轮结束前自检

输出前检查：

- 是否说明了本节代码位置和边界？
- 是否同时说明了函数定义与调用位置？
- 是否遗漏主要函数的内部步骤？
- 是否说明了数据所有者、首地址、shape、size 和访问方式？
- 是否在需要时提供了小型示例？
- 是否把后续操作错误地提前归入本节？
- 是否区分了 Host、微码和 RTL？
- 是否准确使用学习与验证状态？
- 是否给出了紧邻的下一步？
- 是否再次判断了当前内容是否适合写入文档？

# 项目模拟面试统一范式

## 1. 文档定位

本规范用于把简历中的工程项目整理成可复用的数字 IC 模拟面试材料。它不依赖某一个具体项目，可用于 NPU、Cache、总线、数据通路、控制器以及其他 RTL 项目。

统一方法是：

```text
通用面试流程 + 每个项目独立事实卡片 + 分层追问 + 证据边界
```

模拟过程中由同一个讲解 Agent 同时承担面试官和候选人两个角色，但两个角色掌握的信息必须严格隔离。

## 2. 双角色信息边界

### 2.1 面试官角色

面试官在第一轮提问前只能看到：

- 候选人的简历；
- 岗位描述中的能力要求；
- 数字 IC 设计岗位的通用知识。

面试官不能提前知道：

- RTL 内部信号名和状态名；
- 源码行号和未写入简历的实现参数；
- 候选人尚未讲出的 Bug 根因；
- 项目的修改历史；
- 未来方案是否已经实现。

后续追问只能来自两个方向：

1. 候选人上一轮回答中主动暴露的信息；
2. 与该回答直接相关的数字 IC 通用知识。

因此，面试官可以先问“你如何组织 KV Cache”，候选人回答地址维度后再追问地址计算；不能在第一轮直接询问某一行 RTL 的地址拼接是否正确。

### 2.2 候选人角色

候选人的回答只能依据：

- 当前版本源码；
- 仿真日志和回归结果；
- 综合、Implementation 和 STA 报告；
- 简历中的项目描述；
- 已确认的个人工作边界；
- 实际发生并完成复盘的 Bug。

回答时必须区分以下状态：

| 状态 | 含义 |
|---|---|
| 已设计 | 已形成明确架构或微架构方案 |
| 已实现 | 已落到当前 RTL 或软件代码 |
| 已仿真验证 | 已有可复现仿真命令和结果 |
| 已综合 | 已有对应 RTL 版本的综合报告 |
| 已完成 Implementation | 已有布局布线和时序结果 |
| 未来计划 | 仅是下一版优化方案，不能描述为现有能力 |

## 3. 每个项目的事实卡片

开始模拟面试前，先为项目建立事实卡片。事实卡片是回答依据，不直接作为面试官的已知信息。

| 类别 | 必须整理的内容 |
|---|---|
| 项目目标 | 面向什么场景，解决什么问题 |
| 项目边界 | 原型、子系统还是完整产品 |
| 个人贡献 | 自己设计、实现、验证和协作的部分 |
| 顶层架构 | 模块划分及上下游关系 |
| 数据流 | 输入、存储、计算到输出的完整路径 |
| 控制流 | FSM、调度、依赖、握手和协议 |
| 核心参数 | 位宽、阵列规模、容量、频率和配置 |
| 存储结构 | SRAM、FIFO、Cache、Buffer 和外部存储 |
| 验证证据 | Reference、仿真、覆盖率和回归范围 |
| PPA 证据 | 资源、频率、关键路径和功耗来源 |
| 真实 Bug | 现象、定位、根因、修复和回归 |
| 当前限制 | 当前版本没有实现或没有验证的能力 |
| 扩展方向 | 下一版方案及其代价 |

若简历、源码和报告属于不同版本，必须先标记版本差异，再生成回答，不能把旧报告直接归到新 RTL。

## 4. 固定面试路线

### 4.1 第一层：项目开场

面试官先确认项目是什么以及候选人的贡献：

1. 请介绍一下这个项目。
2. 项目解决了什么问题？
3. 你具体负责哪些部分？
4. 当前实现完成到了什么程度？
5. 你认为最核心的设计点是什么？

这一层只建立全局认识，不直接进入状态机、地址或寄存器。

### 4.2 第二层：整体架构

候选人完成项目介绍后，再进入系统层问题：

1. 整体架构如何划分？
2. 输入到输出的数据流是什么？
3. 控制流如何组织？
4. 模块之间如何交互？
5. 为什么选择这种架构？

### 4.3 第三层：核心模块

只对候选人已经提到的模块继续深入：

1. 模块输入输出是什么？
2. 内部状态机如何运行？
3. 数据存在哪里，shape 和位宽是什么？
4. 接口如何握手，如何处理反压？
5. 边界条件如何处理？
6. 为什么这样设计？

### 4.4 第四层：架构取舍

在理解实现后，再考查设计判断：

1. 为什么不用另一种实现？
2. 当前方案牺牲了什么？
3. 面积、性能和验证复杂度如何平衡？
4. 哪些设计适合原型但不适合量产？
5. 如果需求变化，最先受影响的是哪里？

### 4.5 第五层：性能与 PPA

所有性能和 PPA 问题都要建立证据链：

1. 理论峰值如何计算？
2. 实际吞吐为什么低于峰值？
3. 性能数据如何测量？
4. 资源主要消耗在哪里？
5. 关键路径是什么？
6. 如果时序、面积或功耗不达标，优先修改哪里？

必须区分理论计算、静态估算、仿真周期、综合结果和 Implementation 结果。

### 4.6 第六层：验证与 Bug

这一层用于判断候选人是否真正参与 RTL：

1. 验证环境如何搭建？
2. Reference Model 如何使用？
3. 如何区分软件、接口和 RTL 问题？
4. 遇到过哪些真实 Bug？
5. 如何定位和修复？
6. 修复后增加了什么回归？

Bug 回答统一遵循：

```text
现象 -> 缩小范围 -> 定位方法 -> 根因 -> RTL 修改 -> 新增测试 -> 回归结果
```

### 4.7 第七层：项目关联八股

八股优先从项目回答自然引出：

| 项目触发点 | 可追问的数字 IC 基础 |
|---|---|
| 同步 SRAM | 同步读、读写冲突、BRAM 推断 |
| FSM | Moore/Mealy、状态编码、Latch、非法状态 |
| Valid/Ready | 握手、反压、吞吐、FIFO |
| 综合和 STA | Setup/Hold、WNS/TNS、多周期路径 |
| 多时钟接口 | CDC、亚稳态、异步 FIFO、Gray Code |
| 复位 | 异步复位、同步释放、复位恢复时间 |
| 总线 | AXI、AHB、APB 的通道和握手 |
| 验证环境 | UVM、Assertion、Code/Functional Coverage |

### 4.8 第八层：独立八股

项目深挖结束后，再安排独立快问快答，系统覆盖 RTL 编码、FSM、FIFO、CDC、STA、SRAM、Cache、AMBA、低功耗、综合和 UVM。

### 4.9 第九层：开放设计题

最后才进入扩展和反设计问题：

1. 性能要求提高时如何修改？
2. 面积预算降低时如何取舍？
3. 数据规模扩大时如何调整存储和计算？
4. 加入外部存储后如何设计 DMA 和双缓冲？
5. 下一版最值得优化的部分是什么？

开放题必须先复述当前实现，再说明修改点、收益、代价和验证方案。

## 5. 四级追问模型

同一主题按照四级深度递进：

| 级别 | 提问依据 | 示例 |
|---|---|---|
| L1 简历级 | 简历直接描述 | 你实现了 KV Cache，能介绍它的作用吗？ |
| L2 架构级 | 候选人的总体回答 | Prefill 和 Decode 分别如何访问它？ |
| L3 实现级 | 候选人已讲出的实现 | 为什么一个 KV 向量设计成 128 bit？ |
| L4 压力级 | 当前方案和指标 | 序列增长后，哪个数据通路最先成为瓶颈？ |

禁止从 L1 直接跳到源码状态名、某个寄存器或已知 Bug 根因。

## 6. 候选人回答结构

每个回答采用五步结构，但口头表达时保持自然，不机械报出标题：

1. **直接结论**：第一句话回答面试官的问题。
2. **真实实现**：说明当前架构、数据流和关键参数。
3. **设计原因**：解释为什么这样做以及解决了什么问题。
4. **证据边界**：给出公式、日志或报告，并说明未验证范围。
5. **自然引导**：留下一个可继续追问的技术点。

示例：

> 我采用按层复用片上 SRAM，而不是让完整模型权重常驻。当前片上容量无法容纳全部权重，因此 Host 根据 offset 装载当前层数据，完成计算后下一层复用同一地址。这样控制了片上容量，也为后续接入 DRAM 和 DMA 留出了明确的数据搬运边界。

## 7. 三种模拟模式

### 7.1 双角色答案库模式

默认用于整理和背诵：

```text
面试官问题
候选人口语回答
面试官自然追问
候选人继续回答
```

### 7.2 实时模拟模式

面试官每次提出 1 至 3 个问题并等待候选人作答，然后从准确性、口语表达、证据边界和可能追问四方面反馈。

### 7.3 压力面试模式

面试官针对模糊表述连续追问“为什么、如何证明、具体做了什么、属于哪个版本、为什么不用另一种方案”，用于检查候选人能否守住技术边界。

## 8. PPA 回答规则

| 数据类型 | 回答要求 |
|---|---|
| 理论值 | 给出公式和前提 |
| 静态估算 | 明确说明基于容量、位宽或访问次数估算 |
| 仿真数据 | 说明测试输入、统计范围和周期口径 |
| 综合数据 | 说明器件、约束和 RTL 版本 |
| Implementation 数据 | 说明 WNS、TNS、资源和报告版本 |
| 功耗数据 | 说明工具、活动率和时序网表来源；未测量时明确标注 |

## 9. 禁止事项

- 面试官不能引用简历中没有出现且候选人尚未讲出的代码细节。
- 不能在问题中提前给出 Bug 根因。
- 不能把架构澄清包装成真实 Bug。
- 不能把未来优化描述成已经实现。
- 不能把 Verilator 通过描述成 FPGA 板级验证通过。
- 不能把旧版本 PPA 报告直接用于新版本 RTL。
- 不能每个问题都强行转成架构优化。
- 不能只给标准答案而不结合项目实际实现。

## 10. 跨项目复用流程

```text
读取简历和岗位要求
-> 阅读项目代码、文档和报告
-> 建立项目事实卡片
-> 检查简历、源码和报告版本
-> 生成顶层问题
-> 逐层生成实现和取舍问题
-> 插入项目关联八股
-> 补充 PPA、Bug 和验证问题
-> 进行开放设计追问
-> 整理成双角色答案库
-> 进入实时或压力模拟
```

## 11. 每批输出规范

- 每批默认包含 10 至 15 道主问题。
- 顶层问题必须排在模块和代码细节之前。
- 主问题只能来自简历或上一轮回答。
- 回答使用第一人称和可直接口述的语言。
- 每道题至少给出一个明确结论。
- 每批兼顾架构、实现、取舍、证据和能力边界。
- 内容经用户确认后再写入项目题库，并同步维护表格目录和状态。
